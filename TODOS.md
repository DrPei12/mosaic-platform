## Billing and Recovery

### Reserve balance atomically at request acceptance

**What:** Select price and write idempotency, reservation, request/job and outbox in one PostgreSQL transaction.

**Why:** Current workers reserve promotional credit only after an HTTP request has already been accepted and queued, allowing overcommit and task/ledger drift.

**Context:** Reuse the existing row-locking billing service and append-only ledger. Capture or release in the terminal transaction or through a durable settlement outbox. Preserve Provider cost separately from customer price.

**Effort:** L
**Priority:** P0
**Depends on:** Immutable price and routing facts; real PostgreSQL concurrency fixture

### Add fenced generation recovery and operator reconciliation

**What:** Add generation worker owner, lease expiry, fencing token, Inbox events, `submitted_unknown` recovery claims and auditable operator resolution.

**Why:** A crash after a chargeable Provider submission can currently leave a reservation permanently held with no safe claimant, or permit stale writes.

**Context:** Every state transition and external-action registration must verify the current fencing token. Unknown submissions must query by stable Provider correlation when possible and never blind-retry paid work.

**Effort:** L
**Priority:** P0
**Depends on:** Atomic billing acceptance; Provider-specific reconciliation contracts

### Expose reconciliation as a distinct public state

**What:** Add `response.reconciliation_pending` and financial reconciliation states to API, Web and shared contracts.

**Why:** Unknown Provider acceptance is not ordinary failure; collapsing it can trigger duplicate resubmission and incorrect refund expectations.

**Context:** Preserve partial output, show whether funds are frozen, disable unsafe retry and link to a status/operator path until a confirmed final outcome exists.

**Effort:** M
**Priority:** P0
**Depends on:** Fenced generation/chat reconciliation model
